# Godot 4 单机 OCG 对战基础设计

日期：2026-07-26

## 1. 项目目标

本项目使用 Godot 4 开发一款受《游戏王：大师决斗》启发的原创 2D 单机 OCG 对战游戏。规则兼容性建立在 `ygopro-core`（ocgcore）和 Project Ignis 卡片 Lua 脚本之上，而不是在 GDScript 中重新实现 OCG 规则。

长期目标是形成可扩展的完整 OCG 单机框架。首个子项目只交付一个可玩的垂直切片，用最小内容验证规则核心、Godot 前端和原生桥接的完整链路。

## 2. 已确认范围

### 2.1 首版包含

- macOS 桌面端，使用 Godot 4.6.3 或兼容的 4.6 稳定版本。
- 一人控制双方的本地测试对局。
- 两套固定的经典规则测试牌组。
- 真实 ocgcore 裁定和真实 Lua 卡片效果脚本。
- 中文卡片名称、属性、攻守和效果文本。
- 原创 2D 俯视棋盘、卡片动画、连锁提示、粒子和音效反馈。
- 完整的抽卡、阶段推进、召唤、魔陷、基础连锁、战斗和胜负结算流程。
- 调试日志、固定随机种子和可重放的操作序列。

### 2.2 首版不包含

- AI 对手。
- 联网、账号、匹配或服务器。
- 牌组编辑器或任意 `.ydk` 导入。
- 商店、抽卡、任务、个人主页或经济系统。
- 怪兽 3D 模型和王牌怪兽 3D 登场演出。
- 中途保存和恢复完整对局状态。
- Windows 构建与测试。

## 3. 技术路线

采用 Godot GDExtension 原生桥接方案。

`ygopro-core` 编译为 macOS 原生依赖，由精简 C++ GDExtension 管理其 C API。Godot 不直接访问裸 C API，也不在 GDScript 中解析 ocgcore 二进制消息。桥接层将核心消息转换为稳定、结构化的 Godot 事件。

整体数据流：

```text
玩家操作
  → GDScript 对局协调层
  → C++ 响应编码
  → ocgcore 推进规则状态
  → C++ 消息解码
  → Godot 结构化事件队列
  → 2D 动画和界面更新
  → 下一次玩家输入
```

规则计算和动画播放相互解耦。规则核心可以连续产生事件；Godot 按动画节奏消费事件，并在核心要求玩家响应时暂停。

## 4. 分层架构

### 4.1 Godot 表现层

负责：

- 主菜单、设置和决斗场景。
- 棋盘、卡牌节点、区域、信息面板与对话框。
- 鼠标操作、目标高亮与选择反馈。
- 2D 移动动画、粒子、音效和屏幕反馈。
- 卡图按需加载和纹理缓存。
- 本地双人交接遮罩。

表现层不判断召唤条件、发动条件、连锁合法性或伤害裁定。

### 4.2 GDScript 对局协调层

负责：

- 调用原生桥接 API。
- 将结构化核心事件放入动画队列。
- 维护只用于显示的棋盘投影。
- 将用户对合法选项的选择提交给桥接层。
- 在动画、输入请求和场景生命周期之间协调。

显示状态可以从核心查询结果重建，不作为规则真相来源。

### 4.3 C++ GDExtension 桥接层

负责：

- 创建、启动、推进和销毁 ocgcore 对局。
- 管理数据读取器和 Lua 脚本读取器回调。
- 读取并缓存 `cards.cdb` 中的裁定数据。
- 解析 ocgcore 二进制消息。
- 校验并编码玩家响应。
- 向 Godot 暴露结构化事件和错误。
- 记录随机种子、响应序列与核心状态摘要。

C++ 层对 Godot 提供窄接口，避免把 ocgcore 内部结构直接暴露给 UI。

### 4.4 规则与数据层

裁定数据来源：

- 锁定版本的 `edo9300/ygopro-core`。
- 与核心兼容的 Project Ignis CardScripts。
- 与脚本 ID 匹配的 Project Ignis `cards.cdb`。

显示数据来源：

- `data/cards.json` 中的中文名称和效果文本。
- `images/<card_id>.webp` 中的卡图。

发生冲突时，规则和数值裁定以 `cards.cdb + Lua + ocgcore` 为准；中文 JSON 只负责显示。导入阶段必须生成缺失数据、缺失脚本和缺失卡图报告。

### 4.5 本地应用层

负责：

- 两套固定测试牌组。
- 设置和音量。
- 调试模式。
- 对局日志、随机种子和操作记录。

## 5. C++ 与 GDScript 的性能边界

C++ 承担规则执行、数据库访问、脚本读取、二进制解析、响应编码和确定性日志。GDScript 承担 UI、动画和输入。

卡片 JSON 不能在每次显示时全量解析。导入或启动阶段建立轻量索引，运行中按卡片 ID 查询。卡图不得一次全部加载；使用按需加载和有上限的纹理缓存。

目标为 macOS 上稳定 60 FPS。动画卡顿不得影响规则结果；规则错误不得被动画层掩盖。

## 6. 首版牌组

由项目选择两套经典规则测试牌组，不追求竞技强度或复刻现成构筑。牌组必须覆盖：

- 通常召唤和上级召唤。
- 基础特殊召唤。
- 起动、诱发、反转和永续类怪兽效果的代表案例。
- 通常、装备、永续和场地魔法。
- 通常、永续和反击陷阱。
- 目标选择、破坏、送去墓地、除外和攻守变化。
- 基础连锁和战斗步骤响应。

首个垂直切片不要求覆盖融合、同调、超量、灵摆和连接召唤的 UI 流程，但架构不得阻止后续添加。额外召唤法分别作为后续规则测试包交付。

## 7. 界面与交互

### 7.1 布局

- 16:9 横屏，1920×1080 为设计基准。
- 中央为俯视决斗场。
- 左侧为当前卡片详情。
- 右侧为阶段、操作记录、连锁和合法操作。
- 使用 Godot 拉伸策略适配其他窗口尺寸。

棋盘预留双方主要怪兽区、魔陷区、额外怪兽区、场地区、墓地、除外区、主卡组和额外卡组。

### 7.2 操作

- 只高亮核心判定为合法的卡片、区域和目标。
- 点击卡片后只展示核心提供的合法操作。
- 私密选择前显示交接遮罩；调试模式可关闭遮罩。
- 快速点击不能跳过核心输入节点，也不能重复提交响应。

### 7.3 视觉方向

采用原创深色金属与蓝青色能量风格。借鉴《大师决斗》的信息密度、俯视棋盘和操作反馈，但不复用其 UI 素材。

不同事件使用一致的视觉语言：

- 召唤：区域聚光与卡片落位。
- 发动：卡片抬起、发光和连锁编号。
- 破坏：短促碎裂或能量消散。
- 除外：区别于墓地移动的颜色和方向。
- 重要召唤：保留全屏 2D 卡图切入接口。

## 8. 错误处理

- 卡图缺失时使用占位图并继续。
- 规则数据或必需 Lua 脚本缺失时阻止开始对局。
- 错误信息必须包含卡片 ID、脚本或数据路径以及失败阶段。
- 无法解析核心消息时立即暂停对局，保存最近消息、玩家响应、随机种子和日志。
- GDExtension 边界校验所有来自 Godot 的响应参数。
- UI 动画失败时允许跳过动画，并从核心查询重新构建显示状态。

## 9. 测试策略

### 9.1 C++ 单元测试

- 数据库读取和卡片字段映射。
- Lua 脚本路径解析。
- 二进制消息解码。
- 玩家响应编码。
- 非法参数和缓冲区边界。

### 9.2 核心集成测试

使用固定随机种子和固定牌组验证：

- 初始抽卡和回合阶段。
- 通常召唤、特殊召唤和盖放。
- 攻击、战斗伤害和破坏。
- 魔陷发动、连锁响应和连锁结算。
- LP 归零、卡组耗尽等胜负条件。

### 9.3 Godot 无界面测试

- 结构化事件队列顺序。
- 显示棋盘投影。
- 输入请求只接受合法选项。
- 场景退出时正确销毁原生对局。

### 9.4 可视化冒烟测试

通过 Godot MCP：

- 启动工程和指定场景。
- 读取编辑器及运行时错误。
- 截取关键画面。
- 模拟基础输入并验证主菜单到对局的路径。

## 10. 首个里程碑验收标准

在 macOS 上：

1. 从主菜单开始一场固定牌组测试决斗。
2. 一名用户可以控制双方完成完整对局。
3. 可以进行抽卡、阶段推进、召唤、盖放、魔陷发动、基础连锁、战斗和胜负结算。
4. 所有合法性和裁定来自真实 ocgcore 与 Lua 脚本。
5. 中文卡片信息与现有 WebP 卡图可以正确显示。
6. 对局过程中没有未处理的 GDExtension、Lua 或 Godot 错误。
7. 固定种子和操作记录能够复现测试对局中的规则结果。

## 11. 依赖与分发约束

`ygopro-core` 和相关 Project Ignis 资源包含各自的开源许可证要求。项目必须锁定依赖版本、保留许可证和来源说明，并在公开分发前完成 AGPL 及其他素材授权审查。

游戏王名称、卡片图像和卡片文本涉及第三方知识产权。本项目当前按个人、非商业、离线开发处理；任何公开发布或商业化决定都必须单独评估授权风险。
