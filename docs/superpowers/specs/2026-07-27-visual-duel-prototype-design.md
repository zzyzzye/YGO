# 黑白可视化决斗原型设计

## 目标

把现有居中的文字诊断页替换为一个以 `1280×720` 为基准的黑白 2D 决斗场，
直接展示真实卡图、双方手牌和场地区域，并通过真实前端交互驱动 OCGCore。

首个可玩版本必须支持：

1. 玩家固定在画面下方，对手固定在画面上方。
2. 双方主卡组、额外卡组、墓地、除外区、5 个怪兽区和 5 个魔法陷阱区。
3. 玩家手牌显示真实卡图；对手手牌显示卡背。
4. 悬停卡片时显示放大卡图、中文卡名、类型和描述。
5. 点击玩家手牌后，仅展示 OCGCore 当前允许的召唤、怪兽盖放、魔陷盖放和发动动作。
6. 支持取消选择和结束回合。
7. 完成至少一次“选手牌—执行合法动作—场面更新—结束回合—对手抽牌”的流程。
8. 使用 Godot MCP 检查布局、卡图、输入、状态变化和运行错误。

本阶段使用黑白功能风格，不制作复杂主题皮肤、粒子、音效、联网、AI 决策或
完整动画系统。真实卡图保留原色，用于快速辨认和验证素材链路。

## 画面与分辨率

项目继续采用 `1280×720` viewport 和 `canvas_items` 拉伸。决斗场占据主画面，
不再用诊断文字决定内容宽度。

布局分为三列：

- 左侧约 220 像素：选中卡详情，包含 `160×232` 左右的放大卡图、中文名、
  类型和可滚动描述。
- 中间约 820 像素：双方场地、手牌与阶段提示。
- 右侧约 200 像素：当前动作、回合信息、LP、取消、结束回合和重新开局。

中间区域从上到下依次为：

- 对手手牌。
- 对手魔法陷阱区、怪兽区。
- 中央回合/阶段分隔带。
- 玩家怪兽区、魔法陷阱区。
- 玩家手牌。

牌组、额外牌组、墓地和除外区放在各自行的两侧。区域使用深灰填充、白色或浅灰
边框和中文短标签；可用目标用白色高亮，不可用区域保持暗灰。

诊断信息移入 `F1` 可切换的半透明覆盖层，包含 Godot/OCGCore 版本、当前消息号、
处理状态、双方区域计数和最近错误。覆盖层默认关闭。

## Godot 组件边界

为避免继续扩大单一 `main.gd`，界面拆成可复用组件：

- `CardView`：显示正面卡图或统一卡背，处理悬停、选中、高亮和点击信号。
- `ZoneView`：表示一个场地区域，显示标签、卡片数量和区域顶牌。
- `HandView`：根据卡片列表创建带重叠布局的 `CardView`。
- `DuelBoard`：组织双方区域、手牌、详情面板和动作面板。
- `Main`：只负责桥接初始化、建局和把后端快照交给 `DuelBoard`。

卡图统一通过卡片数据库返回的 `res://images/<id>.webp` 加载。加载失败时显示带
卡号的黑白占位卡，不阻断对局。

## OCGCore 消息与动作模型

### 空闲阶段候选

扩展现有 `MSG_SELECT_IDLECMD` 解析器，完整读取六类候选：

1. 通常召唤。
2. 特殊召唤。
3. 表示形式变更。
4. 怪兽盖放。
5. 魔法陷阱盖放。
6. 发动效果。

首个版本对前端暴露通常召唤、怪兽盖放、魔法陷阱盖放和发动效果。特殊召唤和
表示形式变更可以解析并显示为“尚未接入”，但不得伪造响应。

每个候选值至少包含：

- `action_kind`
- `index`，即该候选在对应 OCGCore 列表中的索引。
- `card_id`
- `controller`
- `location`
- `sequence`
- 发动效果额外包含 `description` 和 `client_mode`。

### 语义接口

`DuelSession` 继续独占二进制响应协议，并新增：

- `submit_idle_action(kind, index)`
- 对 `kind/index` 做当前待决策快照校验。
- 根据 `MSG_SELECT_IDLECMD` 协议构造 `int32((index << 16) | type)`。
- 提交后推进到下一玩家决策或明确的不支持消息。

Godot 桥接层暴露：

- `get_duel_snapshot() -> Dictionary`
- `submit_idle_action(action_kind: String, index: int) -> Dictionary`
- 现有 `submit_end_turn()` 可内部复用统一动作提交。

`get_duel_snapshot()` 返回：

- 当前处理状态和待决策。
- 双方 LP、回合玩家和阶段。
- 双方手牌卡片列表。
- 双方各区域的卡片列表或至少可见顶牌。
- 当前空闲阶段候选动作。

隐藏信息约束：

- 玩家手牌返回真实卡号。
- 对手手牌只返回数量，前端显示卡背。
- 后端未来可扩展观察者视角，但首个版本不泄露对手手牌卡号。

## 查询策略

单纯的 `OCG_DuelQueryCount` 不足以渲染卡图。新增窄查询接口，使用
`OCG_DuelQuery` 请求指定玩家和区域的卡号、控制者、位置、序号和表示形式。

查询解析必须：

- 在 C++ 中完成长度校验。
- 明确处理空区域。
- 不把 OCGCore 缓冲区指针泄露到 Godot。
- 对不可见卡返回 `card_id=0` 或仅返回数量。
- 以区域和序号排序，确保相同种子下界面顺序稳定。

如果完整区域查询在当前 OCGCore 版本的字段格式需要额外探索，第一阶段可从
`MSG_DRAW`、`MSG_MOVE` 和当前玩家手牌候选维护可见状态，但最终快照必须以查询
结果校正，避免前端成为第二规则源。

## 前端交互

1. 刷新快照并渲染玩家手牌。
2. 玩家点击一张手牌。
3. `DuelBoard` 根据候选动作中过滤相同 `location/sequence/card_id` 的项目。
4. 右侧显示这张卡当前真实可用的动作按钮。
5. 点击动作后调用语义接口；按钮不直接构造字节。
6. 后端校验候选仍属于当前决策后提交 OCGCore。
7. 返回新快照并重绘手牌和场地。
8. 任何错误都保留当前画面，在右侧显示中文诊断。

不存在合法动作的手牌仍可选中查看，但动作区显示“当前没有可执行动作”。

## 测试与验收

### 原生测试

- 每类 `MSG_SELECT_IDLECMD` 候选使用至少一个非空元素，验证字段宽度和索引。
- 非法动作类型、越界索引和过期待决策必须被拒绝且不得写响应。
- 真实素材集成测试至少执行一次合法通常召唤或盖放，并验证手牌减少、对应场区增加。
- 固定牌组与种子重复运行时，候选列表和关键区域结果一致。

### Godot 无头验证

- 场景与脚本可解析。
- 卡图路径可以加载。
- 后端初始化和开局没有项目自身错误。

### Godot MCP 验收

- 截图确认为 `1280×720` 黑白场地，而不是文字诊断页。
- 玩家手牌出现 5 张真实卡图，对手手牌出现 5 张卡背。
- 悬停或点击后详情区显示对应真实卡图和中文资料。
- 点击一张具有合法动作的手牌，只出现 OCGCore 返回的动作。
- 完成一次召唤、盖放或发动后，手牌和场区同步变化。
- 点击结束回合后，对手手牌数量增加且回合玩家切换。
- `F1` 可打开和关闭诊断层。
- 调试输出没有项目自身的 GDScript、GDExtension 或 OCGCore 错误。

## 完成标准

只有同时满足以下条件才完成本目标：

- 黑白决斗场取代旧诊断页。
- 真实卡图、双方手牌、完整区域框架和卡片详情可见。
- 召唤、盖放、发动的入口由真实 OCGCore 候选驱动。
- 至少一种场上动作实际改变 OCGCore 区域状态。
- 结束回合流程继续有效。
- 原生测试、Godot 无头验证和 Godot MCP 交互验收全部通过。
