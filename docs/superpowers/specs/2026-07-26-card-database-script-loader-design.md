# 卡片数据库与正式卡脚本加载设计

## 1. 目标

本阶段为单机决斗建立可复用的卡片数据基础层。C++ 负责解析
`data/cards.json`、筛选可用卡片、生成二进制缓存、向 OCGCore 提供规则
字段，并从固定的 ProjectIgnis 正式卡目录加载 Lua 脚本。Godot 只通过
GDExtension 查询状态和展示数据，不在 GDScript 中承担大批量 JSON
解析或规则字段转换。

完成后，项目应能使用真实卡片数据和正式卡 Lua 脚本创建 OCGCore
决斗实例，并在诊断界面查询和展示一张实际卡片。

本阶段不实现卡组编辑、洗牌、抽卡、指令响应或完整决斗协议。

## 2. 数据范围

### 2.1 正式卡范围

Lua 规则仅使用 `third_party/CardScripts` 中的基础脚本和
`third_party/CardScripts/official/` 中的正式卡脚本。首版不加载
`pre-release/`、`pre-errata/`、`rush/`、`skill/` 或 `unofficial/`
目录。

### 2.2 卡片与卡图交集

首版数据库只收录同时满足以下条件的记录：

1. `cards.json` 中存在非零 `id`。
2. `data` 对象及其必要规则字段有效。
3. `cn_name` 非空。
4. `images/<id>.webp` 存在。

当前素材统计为：

- JSON 记录：14,248 条。
- 无有效规则数据的记录：42 条。
- 有效规则卡：14,206 张。
- 卡图：14,110 张。
- 有规则数据但缺少卡图：96 张。
- 首版最终交集：14,110 张。

以上数量用于当前素材的回归测试。以后数据源更新时，程序应根据实际
内容重新统计，而不是把数量写死为运行逻辑。

### 2.3 标识符对应关系

`cards.json` 的外层键和 `cid` 是来源站点的内部编号；`id` 是规则卡号。
数据库唯一主键使用 `id`。

对应关系如下：

```text
JSON 外层键 / cid
        ↓
规则卡号 id
        ├── images/<id>.webp
        ├── third_party/CardScripts/official/c<id>.lua
        ├── OCGCore 卡片查询 code
        └── 后续卡组文件中的卡号
```

`cid` 作为来源信息保留，但不参与 OCGCore 查询。

## 3. 架构

### 3.1 CardDatabase

`CardDatabase` 是运行时卡片数据的唯一入口，职责包括：

- 解析 `cards.json`。
- 检查记录有效性和对应卡图。
- 只保留约定的交集。
- 以 `id` 建立常数时间查询索引。
- 同时保存展示数据和 OCGCore 规则字段。
- 向 Godot 和 `DuelSession` 提供只读查询接口。

调用方不应依赖 JSON 的内部结构。以后更换解析器或数据来源时，
`DuelSession` 和 Godot 桥接接口保持不变。

### 3.2 CardCache

`CardCache` 管理开发阶段缓存：

```text
/Volumes/WD/YGO/.cache/cards/card_database.bin
```

`.cache/` 必须加入 Git 忽略规则。缓存头至少包含：

- 固定魔数。
- 缓存格式版本。
- JSON 数据指纹。
- 卡图清单指纹。
- 记录数量。
- 数据区长度或校验信息。

数据源或格式版本变化时缓存自动失效。写入时先在同一目录生成临时
文件，完整写入并关闭成功后再替换正式缓存，避免进程中断留下半个
有效文件。

独立应用发布后，应用包可能为只读。发布版可把缓存根目录切换到
Godot 的 `user://cache/cards/`，但本阶段的开发缓存必须留在项目目录。

### 3.3 OfficialScriptLoader

`OfficialScriptLoader` 向 OCGCore 提供脚本读取回调，职责包括：

- 加载 OCGCore 初始化所需的 CardScripts 基础 Lua 文件。
- 按需加载 `official/c<id>.lua`。
- 将读取到的 UTF-8 字节原样交给 `OCG_LoadScript`。
- 拒绝绝对路径、父目录跳转和不在允许列表内的规则目录。
- 用中文记录缺失脚本、拒绝路径和脚本加载错误。

普通怪兽或其他无需独立效果脚本的卡可以没有 `c<id>.lua`。只有当
OCGCore 实际请求某个脚本而文件不存在时，才将其视为该次决斗的脚本
错误。

### 3.4 DuelSession

`DuelSession` 不再使用返回空卡片和拒绝全部脚本的临时回调。创建
决斗时，它引用已初始化的 `CardDatabase` 和 `OfficialScriptLoader`，
并把二者作为 OCGCore 回调的载荷。

数据库和脚本加载器的生命周期必须覆盖整个 OCGCore 决斗实例。
`DuelSession` 仍负责决斗句柄的 RAII 创建与销毁。

### 3.5 YgoCoreBridge

Godot 桥接层新增以下能力：

- 初始化卡片数据库。
- 返回缓存命中、缓存重建、卡片数量和错误状态。
- 按规则卡号 `id` 查询展示信息。
- 返回卡图的项目相对路径。
- 创建使用真实数据和脚本回调的决斗。

桥接层不向 GDScript 暴露裸指针、OCGCore 结构体或缓存内部格式。

## 4. 卡片记录

### 4.1 展示字段

缓存保留：

- `id`
- `cid`
- `cn_name`
- `text.types`
- `text.pdesc`
- `text.desc`
- 卡图相对路径

界面主名称固定使用 `cn_name`。不得使用 `md_name`、`sc_name` 或其他
译名覆盖它。当前交集中的全部卡片都具有非空 `cn_name`。

### 4.2 OCGCore 字段

基本映射为：

```text
OCG_CardData.code      ← id
OCG_CardData.type      ← data.type
OCG_CardData.attack    ← data.atk
OCG_CardData.defense   ← data.def
OCG_CardData.race      ← data.race
OCG_CardData.attribute ← data.attribute
OCG_CardData.setcodes  ← data.setcode 拆分结果
```

等级、阶级、灵摆刻度和连接标记必须按照 YGOPro 数据格式与卡片类型
解析，不能把所有卡都按普通怪兽处理：

- 未知攻击力或守备力保留 OCGCore 约定的负数值。
- Link 怪兽的 `data.def` 解释为连接标记，不解释为守备力。
- Xyz、Link 和灵摆卡正确处理等级、阶级与刻度。
- `setcode` 拆分为以零结尾的 `uint16_t` 数组。
- `setcodes` 内存由卡片数据层管理，其生命周期覆盖 OCGCore 读取完成
  回调。

字段解析必须由针对代表性卡片的测试固定，避免仅凭字段名称推断。

## 5. 二进制缓存约束

缓存只写入明确规定的固定宽度整数、长度字段和 UTF-8 字节串。不得把
C++ 指针、`std::string`、容器对象或带有编译器相关填充的结构体原样
写入文件。

读取器必须在分配或读取前检查：

- 魔数和格式版本。
- 文件总长度。
- 记录数量的合理上限。
- 每段字符串和数组的长度。
- 数据区剩余字节数。
- 主键重复。

任一检查失败都把缓存视为损坏。损坏缓存不应导致崩溃或越界访问，而
应输出中文警告并从 JSON 自动重建。

## 6. 启动数据流

1. Godot 调用 `YgoCoreBridge` 初始化卡库。
2. C++ 定位 `cards.json`、`images/`、CardScripts 和缓存目录。
3. C++ 计算数据源指纹并检查缓存。
4. 缓存有效时直接加载。
5. 缓存不存在或无效时解析 JSON、筛选交集并重建缓存。
6. `OfficialScriptLoader` 校验基础脚本目录。
7. `DuelSession` 使用真实卡片与脚本回调创建 OCGCore 决斗。
8. Godot 查询状态和测试卡片并更新诊断界面。

缓存重建应输出一条中文汇总日志，例如：

```text
卡片缓存构建完成：收录 14110 张，跳过无效记录 42 条，跳过缺图卡片 96 张。
```

## 7. 错误处理

- `cards.json` 不存在或无法解析：初始化失败，阻止进入游戏并返回中文
  错误。
- 卡图目录不存在：初始化失败，因为首版数据范围依赖交集。
- 缓存损坏：输出中文警告并自动重建。
- 单张卡片不存在：返回明确的未找到状态，不抛出异常到 Godot。
- 必需基础 Lua 文件缺失：阻止创建决斗。
- OCGCore 请求的单卡脚本缺失：记录卡号和规范化路径，并使该次脚本
  加载失败。
- 缓存建立后某张卡图被删除：查询返回缺图状态，不造成崩溃。
- 路径越界或非正式卡目录请求：拒绝并输出中文安全警告。

所有项目自有打印、日志、警告、错误和诊断文字使用简体中文。第三方
库原始输出可以保留，但项目转述时补充中文上下文。

## 8. 测试策略

采用测试驱动开发，至少覆盖：

- 普通怪兽、效果怪兽、融合、Xyz、灵摆和 Link 代表卡的字段解析。
- `id` 到 JSON、卡图和 Lua 脚本的对应关系。
- 当前素材的 14,110 张交集结果。
- 42 条无效记录和 96 张缺图卡的筛除。
- 首次构建与第二次缓存命中的数据一致性。
- JSON 或卡图清单变化导致缓存失效。
- 截断、错误版本或恶意长度缓存的安全重建。
- 重复主键的拒绝。
- 脚本路径规范化和越界拒绝。
- 基础 Lua 文件加载。
- 真实回调下的 OCGCore 决斗创建与销毁。
- Godot 按 `id` 查询 `cn_name`、描述和卡图路径。
- 项目自有错误和状态信息为中文。

测试使用小型临时夹具验证解析和缓存边界；仅在集成测试中读取完整本地
素材，避免单元测试依赖 14,110 张卡图。

## 9. 诊断界面

诊断界面展示真实加载结果：

```text
Godot 4.6.3
OCGCore 11.0
正式卡片：14110
缓存：已就绪
测试卡片：青眼白龙（89631139）
Lua 规则：已连接
```

数量来自运行时数据库，不在界面脚本中写死。初始化失败时，界面显示
中文错误摘要，并把详细原因写入错误日志。

## 10. 完成标准

满足以下条件即完成本阶段：

1. C++ 能从当前素材生成并重新加载安全的二进制缓存。
2. 数据库只包含已确认的正式卡与卡图交集。
3. OCGCore 卡片回调返回正确字段和稳定的 `setcodes` 生命周期。
4. 正式卡基础 Lua 与按需单卡脚本能够安全加载。
5. 使用真实数据和脚本回调创建、查询状态并销毁决斗成功。
6. Godot 诊断界面显示真实卡片数量和青眼白龙信息。
7. 自动测试、原生构建和 Godot 无头启动全部通过。
8. 项目自有日志、错误和诊断输出符合中文要求。
