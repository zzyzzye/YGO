# 大师决斗式场地与 UI 布局重构设计

## 目标

把当前“上下表格排列”的规则验证界面重构为接近《游戏王：大师决斗》
的信息空间布局。此次只处理场地骨架、HUD 位置、手牌层级和响应式关系；
继续沿用现有黑白原型 Theme，不复刻官方材质、光效、动画或受版权保护的
美术资源，也不新增 OCGCore 决策类型。

成功标准不是像素级临摹，而是玩家第一眼能够识别出：

- 中央是一块连续的双方决斗场，而不是五行表格；
- 玩家手牌悬浮在近端，对手手牌收纳在远端；
- 双方主怪兽区、魔陷区有明确近远层次；
- 玩家状态、对手状态、阶段和系统工具属于独立 HUD，不占用棋盘行高；
- 1920×1080、3840×2160 和 16:10 使用同一场景结构与布局逻辑。

## 当前问题

`DuelBoard/Battlefield` 使用 `VBoxContainer` 依次放置对手手牌、四行卡位、
中央文字和玩家手牌。这会导致所有内容共享纵向分配，产生以下结构问题：

- 双方区域尺寸相同，没有远端压缩和视觉纵深；
- 手牌成为棋盘的一行，挤压主场地；
- 中央回合文字切断棋盘；
- HUD 以零散锚点覆盖在四角，和场地没有稳定的信息层级；
- 卡位标题与大面积空框占据过多空间，实际卡牌反而偏小；
- 后续额外怪兽区、场地区、卡组和墓地没有自然的扩展位置。

## 方案选择

### 方案 A：继续调整现有 VBox

优点是改动小，现有测试路径变化少；缺点是 Container 仍会强制所有场地行
参与同一纵向分配，无法形成手牌悬浮、远端压缩和 HUD 独立层。放弃。

### 方案 B：二维锚点棋盘骨架（采用）

使用一个全屏 `Control` 作为舞台，将棋盘、手牌、左右 HUD 分成独立层。
棋盘内部仍用 Container 管理每一排五个卡位，但各排由锚点和比例尺寸定位。
对手侧整体缩小，玩家侧保持较大尺寸；手牌作为独立前景层覆盖近端棋盘。

此方案能保留 Godot 原生响应式能力，现有 `ZoneView`、`HandView` 和输入信号
也可继续复用，重构风险可控。

### 方案 C：自定义透视投影容器

通过脚本或 Shader 对整块棋盘做梯形投影，视觉更接近 3D 场地，但输入命中、
多分辨率适配和卡牌旋转都会明显复杂化。黑白功能原型阶段不采用。

## 场景结构

`DuelBoard` 保持根节点不变，内部重组为以下层次：

```text
DuelBoard
├── Background
├── FieldStage
│   ├── OpponentField
│   │   ├── OpponentSpellRow
│   │   └── OpponentMonsterRow
│   ├── CenterLane
│   └── PlayerField
│       ├── PlayerMonsterRow
│       └── PlayerSpellRow
├── HandLayer
│   ├── OpponentHand
│   └── PlayerHand
├── HudLayer
│   ├── OpponentHud
│   ├── PlayerHud
│   ├── TurnPhaseHud
│   └── SystemTools
└── OverlayLayer
    ├── StatusToast
    ├── CardDetailOverlay
    ├── ActionBox
    ├── ConfirmationOverlay
    └── DebugOverlay
```

场景仍以 `.tscn` 和 Theme 资源表达稳定结构。GDScript 只负责绑定快照、按
视口比例微调紧凑模式和转发信号，不动态重建整套场地。

## 空间规则

### 棋盘

- 棋盘位于屏幕中央，约占 16:9 视口宽度的 58%～66%、高度的 68%～76%。
- 玩家场地占棋盘近端约 54%，对手场地占远端约 42%，中央留窄分隔带。
- 对手两排整体缩放到玩家排的约 82%～88%，形成轻量纵深，但保持矩形卡位，
  不使用会破坏点击命中的假透视。
- 魔陷区靠各自外侧，怪兽区靠中央；双方排列方向保持现有语义索引，不由
  Godot 重新解释 OCGCore sequence。
- 中央不再放大段回合文字，只保留细窄分隔和必要的决策指示。

### 手牌

- 玩家手牌独立悬浮于底部中央，允许覆盖玩家魔陷区下沿，但不遮挡系统按钮。
- 对手手牌缩小后位于顶部中央，只显示卡背数量。
- 第一阶段保持 `HandView` 的水平排列，不实现弧形旋转；弧形手牌作为后续
  动画与交互任务，避免本次同时改变点击几何。

### HUD

- 对手 HUD 固定在左上或右上外缘，玩家 HUD 位于相对的近端外缘，均包含
  LP 与卡组/墓地摘要，不占棋盘 Container 空间。
- 回合与阶段合并为右侧中部的固定控件；不再把 `TurnLabel` 插入棋盘。
- 重开、信息、退出保持右下角独立工具组，在任何规则决策和无法映射状态下
  都可点击。
- 状态提示位于左侧 HUD 邻近区域；确认与动作浮层继续置于棋盘上方，
  但不得改变场地本身的尺寸。

## 响应式策略

- 1920×1080 为基准，所有主体使用锚点、Container、Size Flags 和最小尺寸。
- 3840×2160 只提高整体缩放与留白，不增加额外布局分支。
- 1920×1200 利用额外高度增加手牌和棋盘间距，卡位索引与 HUD 方位不变。
- 窄屏下优先缩小外侧 HUD 和场地横向留白；不得让手牌、阶段控件或系统工具
  覆盖确认按钮。
- 卡位最小点击尺寸由 `ZoneView` 统一约束，不能只追求视觉缩小。

## 数据和规则边界

- C++/GDExtension 快照、合法候选、响应编码和隐私门禁完全不变。
- `DuelBoard` 继续消费现有字段并提交稳定候选索引或语义参数。
- 本次只移动节点和调整视觉层级，不修改生命值、卡牌位置或胜负状态。
- 尚未实现的额外怪兽区、场地区、卡组、墓地和除外区只预留空间，不创建
  可点击伪区域；待 C++ 暴露合法语义后再接入。

## 测试与验收

- 更新场景契约测试，断言棋盘、手牌、HUD 和 Overlay 属于独立层。
- 更新响应式测试，在 1920×1080、3840×2160、1920×1200 下检查：
  - 玩家手牌位于棋盘前景且不挤压场地；
  - 对手场地区域小于玩家场地区域；
  - 四排卡位不重叠，确认框和系统工具可见；
  - 所有已有攻击、表示形式、连锁、区域和 EffectYN 输入路径仍通过。
- 使用 Godot MCP 读取真实场景树和关键 Rect，并在三种分辨率截图验收。
- 原生 OCGCore 测试保持全量通过，证明布局重构未越过规则边界。

## 非目标

- 不复制《大师决斗》的贴图、字体、音效、角色或场地资产。
- 不在本任务实现 3D 相机、梯形 Shader、弧形手牌或召唤动画。
- 不实现额外怪兽区、场地区等尚未具备 C++ 语义映射的区域交互。
- 不改变已经完成的攻击、表示形式、连锁、基础五区与 EffectYN 规则流程。
